# 系统设计与二开方案

> 版本：V0.1  
> 原则：最大化复用 yf-boot-exam，优先修复数据正确性和权限边界

## 1. 现有技术架构

```text
Vue 3 + TypeScript + Element Plus
              |
              | HTTP / JSON / token header
              v
Spring Boot 3.2.1 + Shiro + JWT
              |
       +------+------+
       |             |
     MySQL          Redis
       |
     Quartz JDBC JobStore
```

现有模块可以复用：

- `system/modules/user`：用户、注册、状态和账号密码。
- `system/modules/role`：角色和菜单权限。
- `system/modules/depart`：部门组织结构。
- `modules/exam/repo`：题库、题目和选项。
- `modules/exam/exam`：考试信息、组卷规则和考试记录。
- `modules/exam/paper`：随机试卷、答题、交卷和评分。

## 4. 身份与鉴权设计

### 4.1 正式账号

系统管理员、HR 和员工继续使用 `el_sys_user`、角色、菜单权限、JWT、Redis 和 Shiro。

员工自由注册流程复用 `/api/sys/user/reg`，但需要：

- 注册页面明确显示“员工注册”。
- 注册信息补充姓名、工号、部门等必要字段。
- 手机号和邮箱为选填字段。
- 默认角色为员工。
- 默认启用注册审核，由系统管理员或 HR 审核，审核前不可登录参加考试。

### 4.2 候选人临时身份

候选人不建立自己可见的用户名和密码。HR 创建考核分配时，系统内部创建一个 `el_sys_user` 临时用户并分配候选人角色。

```text
姓名 + 考核码
      |
      v
验证 el_exam_assignment
      |
      v
取得内部 user_id
      |
      v
签发普通 JWT 并写入 Redis
      |
      v
复用现有考试接口
```

候选人验证接口加入 Shiro 匿名白名单；验证完成后的考试接口仍必须经过 JWT 鉴权。

### 4.3 权限矩阵

| 岗位/模板配置 | 是 | 否 | 否 | 否 | 否 |
| 题库/题目维护 | 是 | 否 | 否 | 否 | 可授权 |
| 候选人录入/导入 | 是 | 是 | 否 | 否 | 否 |
| 员工账号审核 | 是 | 是 | 否 | 否 | 否 |
| 发放已有考核 | 是 | 是 | 否 | 否 | 否 |
| 参加本人考核 | 可测试 | 否 | 是 | 是 | 否 |
| 人工阅卷 | 是 | 可选 | 否 | 否 | 是 |
| 全量成绩查看 | 是 | 授权范围 | 仅本人是否通过 | 仅本人是否通过 | 阅卷范围 |

## 5. 考核模板与分配

现有 `el_exam` 应逐步承担“考核模板”角色，记录岗位、场景、时长、及格分和组卷规则。V1 的考生结果展示策略固定为只显示“是否通过”。

实际把某个模板发给某个人时，创建 `el_exam_assignment`：

- 候选人：HR 选择岗位后自动匹配 `ENTRY` 模板。
- 员工：系统管理员或 HR 选择 `ENTRY`、`PROMOTION` 或 `GENERAL` 模板并分配。
- 考核分配保存个人有效时间、状态和最终试卷，不修改模板本身。

场景固定为三种：`ENTRY`（入职/面试）、`PROMOTION`（晋升）、`GENERAL`（通用日常）。外部候选人和新员工都可使用 `ENTRY`，通过 `subject_type` 区分人员类型。

## 6. 随机组卷与快照

现有代码在 Java 中取得题目 ID 后执行 `Collections.shuffle`，可继续用于首期低并发场景。

必须修改以下规则：

1. 只抽取启用状态的题库和题目。
2. 每个考核分配在整个生命周期内只允许存在一份试卷，不设置重考次数。
3. 创建试卷时随机题目顺序。
4. 对单选、多选题的选项独立随机排序。
5. 将题干、解析、选项内容、标准答案复制到试卷表形成不可变快照。
6. 历史试卷展示不得再关联题库当前内容。

现有 `PaperQuMapper.xml` 通过 `qu_id` 回查 `el_repo_qu`，会导致修改题库后历史试卷内容变化，必须在 V1 修复。

## 7. 作答与评分状态

建议试卷状态：

```text
CREATED -> IN_PROGRESS -> SUBMITTED
                              |
                 +------------+------------+
                 |                         |
         无主观题，自动完成           存在主观题
                 |                         |
             COMPLETED              PENDING_REVIEW
                                             |
                                          COMPLETED
```

- 客观题继续采用答案集合完全匹配后得分的规则。
- 多选题是否支持部分得分属于待确认项；V1 默认不支持。
- 简答题保存文本答案，交卷时不计主观题分数。
- 全部简答题完成评分后重新计算总分、通过状态和考试记录。
- 评分修改必须留下阅卷记录，不直接无痕覆盖。
- 最终完成后，候选人和员工接口只返回是否通过；分数、标准答案和解析仅在管理端按权限返回。
- 结果自动公布：无主观题时交卷结算后立即可查；有主观题时完成最终阅卷后立即可查，不增加 HR 发布状态。

## 8. 考核码规则

- 展示形式：固定 6 位大写字母和数字，排除 `0/O`、`1/I` 等易混淆字符。
- 有效期：默认从 `valid_from` 起 14 天，创建表单自动计算 `expire_at=valid_from+14d`；HR 可在发放前调整。
- 唯一范围：一个考核码只对应一条考核分配。
- 保存方式：只保存 BCrypt 等安全哈希；明文只在生成/重置时返回一次。
- 验证条件：姓名匹配、状态可进入、处于有效期、内部用户正常。
- 恢复规则：首次进入后状态变为 `STARTED`，未交卷且未过期仍可重新验证并恢复原试卷。
- 失效规则：交卷完成、人工停用或超过有效期。
- 重考规则：不允许重考；重复开始只恢复原试卷，完成或过期后不得生成新试卷。再次考核必须新建考核分配。
- 防刷规则：同一 IP/考核码连续失败应限速并记录安全日志。

## 9. 关键安全整改

以下项目必须先于正式业务上线完成：

1. 在 Shiro Realm 中真正调用 JWT 签名校验；当前仅解析用户名和过期时间不足以证明 token 未被篡改。
2. 将 JWT 密钥从源码移到环境变量或外部配置。
3. 所有试卷详情、答题卡、保存答案、交卷和实时状态接口校验试卷所有者。
4. 管理接口使用 `@RequiresPermissions` 和数据范围双重限制。
5. 候选人 token 的最长有效期不能超过考核分配截止时间。
6. 创建试卷、保存答案和交卷增加状态校验与幂等保护。
7. 生产环境关闭 Swagger 或限制为管理员网络访问。
8. 生产环境禁止直接暴露 MySQL 3306 和 Redis 6379。

## 10. 兼容与迁移策略

- 保留现有表名和核心类名，避免初期重命名造成大范围回归。
- 使用新增字段和新增模块逐步迁移。
- 旧题目默认迁移为启用状态。
- 旧考试可标记为历史模板；新业务从岗位和场景模板开始。
- 新功能先通过版本化 SQL 迁移脚本安装，不直接依赖手工修改数据库。
- 对旧试卷无法补全真实历史快照时，只保证迁移后的新试卷具有不可变快照。
